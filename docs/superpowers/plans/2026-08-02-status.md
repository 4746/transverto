# Translation Status Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a read-only `ctv status` command that reports filtered translation problems with deterministic human/JSON output and CI-friendly exit thresholds.

**Architecture:** Define stable status contracts in a focused entity module. Implement strict project loading, dictionary flattening, comparison, pattern filtering, summary calculation, and threshold evaluation in an oclif-independent `StatusService`; keep the command responsible only for flags, rendering, and applying the resulting exit code.

**Tech Stack:** Node.js 24.15+, TypeScript 6 ESM, oclif 4, Chalk 6, existing configuration validation and placeholder utilities.

## Global Constraints

- Work only on branch `v2.0.0` and preserve unrelated user changes.
- Runtime remains Node.js `>=24.15`; do not add dependencies or compatibility code for older Node versions.
- Do not add tests or modify test infrastructure; `PLAN.md` explicitly excludes tests from this task.
- The command must not write files, generate types, resolve/call translation engines, or make network requests.
- Analyze configured target languages relative to `langCodeDefault`; coverage percentage, history, and source-code scanning are out of scope.
- Reuse `comparePlaceholders` for `{{name}}`, `{count}`, `%s`, and `%1$s` multiset checks.
- Accept exact key patterns or one `*` at the beginning/end; reject `home.*.title` and every other middle/multiple wildcard pattern.
- Apply all filters to structured findings before formatting and summary calculation.
- Do not add tests; verify with build, lint, help, and isolated manual CLI fixtures.

---

## File Structure

- Create `src/shared/entities/status.ts`: public problem, severity, finding, summary, options, and report contracts.
- Create `src/shared/status.service.ts`: strict read-only project loading, flattening, analysis, filtering, stable ordering, summaries, and fail-threshold calculation.
- Create `src/commands/status.ts`: oclif flags, human/JSON rendering, error mapping, and process exit behavior.
- Modify `README.md`: workflow documentation plus generated `ctv status` command help.

### Task 1: Define status contracts and implement read-only analysis

**Files:**

- Create: `src/shared/entities/status.ts`
- Create: `src/shared/status.service.ts`

**Interfaces:**

- Consumes `IConfig`, `CTV_CONFIG_FILE_NAME`, `validateConfigInput`, and `comparePlaceholders`.
- Produces `StatusService.analyze(options?: IStatusAnalysisOptions): Promise<IStatusReport>` for Task 2.
- Produces stable `TStatusProblem`, `TStatusSeverity`, `TStatusFailOn`, `IStatusFinding`, `IStatusSummary`, and `IStatusReport` contracts.

- [ ] **Step 1: Add the stable public entity contracts**

Create `src/shared/entities/status.ts` with these exact contracts and constant orders:

```ts
export const STATUS_PROBLEMS = ['missing', 'extra', 'empty', 'same', 'placeholder'] as const
export const STATUS_SEVERITIES = ['error', 'warning', 'info'] as const
export const STATUS_FAIL_ON = ['error', 'warning', 'never'] as const

export type TStatusProblem = typeof STATUS_PROBLEMS[number]
export type TStatusSeverity = typeof STATUS_SEVERITIES[number]
export type TStatusFailOn = typeof STATUS_FAIL_ON[number]

export interface IStatusFinding {
  key: string
  language: string
  problem: TStatusProblem
  severity: TStatusSeverity
  sourcePlaceholders: null | string[]
  sourceValue: null | string
  value: null | string
  valuePlaceholders: null | string[]
}

export interface IStatusSummary {
  byProblem: Record<TStatusProblem, number>
  bySeverity: Record<TStatusSeverity, number>
  total: number
}

export interface IStatusAnalysisOptions {
  cwd?: string
  exclude?: string[]
  failOn?: TStatusFailOn
  include?: string[]
  languages?: string[]
  problems?: TStatusProblem[]
}

export interface IStatusReport {
  exitCode: 0 | 1
  failOn: TStatusFailOn
  findings: IStatusFinding[]
  languages: string[]
  source: string
  summary: IStatusSummary
}
```

- [ ] **Step 2: Implement strict config and dictionary loading**

Create `src/shared/status.service.ts`. Add local `isObject`, `readJson`, and `flattenDictionary` helpers. `readJson(file)` must include the exact file path in read/parse errors. `flattenDictionary` must recurse only through plain objects, emit dot-separated leaf keys into `Map<string, string>`, and throw `Translation leaf "<path>" must be a string.` for arrays, numbers, booleans, or null.

Load `<cwd>/.ctv.config.json`, require an object root, and require `languages`, `langCodeDefault`, `basePath`, and `basePathEnum` with the same shapes accepted by `LanguageProjectService.load`. Call:

```ts
validateConfigInput({
  languages: parsed.languages as string[],
  source: parsed.langCodeDefault as string,
  translationsPath: parsed.basePath as string,
  typesPath: parsed.basePathEnum as string,
})
```

Do not validate or resolve `engine`, `engines`, `fallback`, batch, or cache fields: status does not consume them and must make no engine calls. Resolve dictionary files as `path.resolve(cwd, basePath, `${language}.json`)` and reject missing/non-file paths before analysis.

- [ ] **Step 3: Validate and normalize analysis options**

Add focused helpers with these rules:

```ts
const unique = <T>(values: T[]): T[] => [...new Set(values)]
```

- default `failOn` to `error`;
- default languages to configured languages excluding `langCodeDefault`;
- every explicit language must be configured and must differ from the source;
- reject an empty explicit language selection only if one was supplied;
- normalize duplicate languages/problems/patterns while preserving first occurrence;
- validate problems and fail threshold defensively even though oclif supplies options;
- validate each include/exclude pattern as exact, `*`, `prefix*`, or `*suffix` with at most one star and never a star surrounded by non-empty text.

Implement `matchesPattern(key, pattern)` with exact equality, `startsWith`, or `endsWith`; do not use regex or general glob libraries.

- [ ] **Step 4: Generate all five finding types**

For each selected target in selected order, compare source and target maps:

```ts
const SEVERITY_BY_PROBLEM: Record<TStatusProblem, TStatusSeverity> = {
  missing: 'error',
  extra: 'info',
  empty: 'warning',
  same: 'info',
  placeholder: 'error',
}
```

- source key absent from target → one `missing` finding with `value: null`;
- target key absent from source → one `extra` finding with `sourceValue: null`;
- existing target `value.trim() === ''` → `empty`;
- existing non-empty target exactly equal to source → `same`;
- existing target whose `comparePlaceholders(sourceValue, value).matches` is false → `placeholder` with both sorted placeholder arrays.

Every non-placeholder finding must set both placeholder fields to `null`. Missing/extra findings must not receive empty/same/placeholder companions. An existing whitespace value may be both empty and placeholder when required placeholders are absent.

- [ ] **Step 5: Filter, sort, summarize, and calculate exit code**

Apply the AND of these groups to findings: selected language, selected problem, include-match, and not exclude-match. Within include and exclude lists, matching is OR.

Sort with configured selected-language index, then locale-independent key comparison:

```ts
const compareText = (left: string, right: string): number => left < right ? -1 : left > right ? 1 : 0
```

Break same-key ties using `STATUS_PROBLEMS` order. Initialize all summary keys to zero, then increment only from filtered findings so `summary.total === findings.length`.

Calculate `exitCode` after filtering:

```ts
const exitCode = failOn === 'never'
  ? 0
  : failOn === 'warning'
    ? (summary.bySeverity.error + summary.bySeverity.warning > 0 ? 1 : 0)
    : (summary.bySeverity.error > 0 ? 1 : 0)
```

Return object keys in the entity-declared JSON order: `source`, `languages`, `findings`, `summary`, `failOn`, `exitCode`.

### Task 2: Add the `ctv status` command and stable rendering

**Files:**

- Create: `src/commands/status.ts`

**Interfaces:**

- Consumes `StatusService.analyze(options?: IStatusAnalysisOptions): Promise<IStatusReport>` from Task 1.
- Produces the public `ctv status` command with repeatable structured filters, human table output, JSON output, and exit codes 0/1/2.

- [ ] **Step 1: Define oclif metadata and flags**

Create `src/commands/status.ts` extending `Command` directly, because it needs no legacy label behavior. Define examples for default, JSON, target/problem filtering, edge wildcard filtering, and CI warning threshold.

Use these flags:

```ts
static flags = {
  exclude: Flags.string({description: 'exclude exact or edge-wildcard key pattern', multiple: true}),
  'fail-on': Flags.string({
    default: 'error',
    description: 'exit 1 when filtered findings reach this severity',
    options: [...STATUS_FAIL_ON],
  }),
  include: Flags.string({description: 'include exact or edge-wildcard key pattern', multiple: true}),
  json: Flags.boolean({description: 'output a stable JSON status report'}),
  language: Flags.string({description: 'target language code', multiple: true}),
  problem: Flags.string({
    description: 'problem type',
    multiple: true,
    options: [...STATUS_PROBLEMS],
  }),
}
```

Cast only after oclif option validation. Pass arrays through unchanged so the service owns normalization and semantic validation.

- [ ] **Step 2: Implement JSON and human output**

For `--json`, log exactly `JSON.stringify(report, null, 2)` and do not call Chalk.

For human output, print `No translation problems found.` when `findings` is empty. Otherwise print:

```text
SEVERITY  PROBLEM      LANGUAGE  KEY  DETAIL
```

Render severity with Chalk only in human mode. Use `-` for null values. Details must be deterministic and single-line:

- missing: `missing target value`;
- extra: `extra target value`;
- empty: `empty or whitespace-only value`;
- same: `same as source`;
- placeholder: `source=[...] target=[...]`, with arrays serialized by `JSON.stringify`.

After the rows, print source/target selection and both summary maps in fixed problem/severity order. Do not use terminal width, TTY detection, or locale formatting.

- [ ] **Step 3: Apply report and usage exit codes**

Wrap parse/analyze/render in a `try` block. Map all option/config/dictionary errors to:

```ts
this.error(error instanceof Error ? error.message : String(error), {exit: 2})
```

After complete human or JSON output, call `this.exit(report.exitCode)` only when `report.exitCode === 1`. Valid clean/ignored reports return normally with exit 0.
